# KnowledgePilot 优化计划（检索质量 + 效率 + 模型架构）

> 版本：v2.0 · 日期：2026-08-29 · 状态：**P0 与 P1 已实施完成**（92 单测通过）
> 前置：v0.1.0-demo 已跑通（63 单测 + 8/8 e2e），服务可运行
> 原则：**每项优化都有实测依据**。本文档包含 6 项实验结论，其中 3 项**否定了行业常见做法**。
> **第二轮实测（§7）推翻了本文档 v1.0 的两个判断，并发现了两个更根本的缺陷。请先读 §7。**

## 0. 执行摘要

本次优化分两类：**已实测确认的缺陷修复**（P0）与**架构能力扩展**（P1/P2）。

核心结论先行：

1. 🔴 **当前 No-Answer 判定存在严重缺陷**：reranker 绝对阈值 0.3 会把 **40% 的正确命中误杀**为"未找到相关信息"，口语化提问是重灾区。修复后 F1 从 **0.75 → 1.00**。
2. 🟡 **向量化未批量**：逐块调用模型，实测有 **1.6x** 优化空间（40.1s → 25.6s / 120 块），改动仅 3 行。
3. ⚪ **不建议现在做 BM25 混合检索**：实测在当前规模下向量检索 6/6 命中，关键词无增益。
4. ⚪ **已否决"相对判据"方案**：z-score / top1-top2 差值实测 F1 均**低于**朴素绝对阈值，不采用。
5. ✅ **LLM 接入必须 OpenAI 兼容化**：这是支持「局域网部署 / 第三方服务」的唯一低成本路径，也是你明确提出的需求。

## 1. 实测依据（三次实验）

实验脚本位于 `backend/tests/bench/`（随 P0 一并入库），语料为模拟企业制度/合同片段。

### 1.1 实验 A：No-Answer 阈值标定（15 域内 + 15 域外查询）

**信号可分性**：

| 信号 | 域内 min | 域内中位 | 域外 max | 域外中位 | 可分性 |
|---|---|---|---|---|---|
| **v_top1**（bge-m3 余弦） | 0.5731 | 0.6438 | **0.5256** | 0.3698 | ✅ **干净间隙** |
| rr_top1（reranker 分） | **0.0184** | 0.4887 | **0.0280** | 0.0006 | ❌ **重叠** |
| rr_margin | 0.0178 | 0.4879 | 0.0237 | 0.0006 | ❌ 重叠 |

> 域内最低 0.0184 < 域外最高 0.0280 —— reranker 分数**不存在任何可分界线**。

**阈值网格搜索（最大化 F1）**：

| 规则 | F1 | 误杀正确答案 | 漏拒 |
|---|---|---|---|
| **【当前基线】rr_top1 >= 0.30** | **0.7500** | **6 / 15（40%）** | 0 |
| v_top1 >= 0.54 ~ 0.56 | **1.0000** | 0 | 0 |
| AND: v_sim>=0.55 且 rr_top1>=0.01 | **1.0000** | 0 | 0 |

**根因**：bge-reranker-v2-m3 是 cross-encoder，对**口语化改写**的查询给出极低绝对分
（`签了字能反悔吗` → 0.067、`打官司去哪儿解决` → 0.018），虽然它**把正确文档排在了第 1 位**。
即：**reranker 的排序能力是好的，但它的绝对分数不适合做门控。**

### 1.2 实验 B：相对判据能否抗语料增长？（15 篇 vs 35 篇）

我原本假设「z-score 等相对判据比绝对阈值更稳健」，**实测证伪**：

| 信号 | 小语料(n=15) F1 | 大语料(n=35) F1 |
|---|---|---|
| **v_top1（绝对阈值）** | **1.000** | **0.968** |
| z_score | 0.857 | 0.882 |
| gap (top1-top2) | 0.909 | 0.929 |

同时确认：**绝对阈值确实会漂移** —— 语料从 15 增到 35 后，域外查询最高相似度
从 0.5256 涨到 0.5996（偶然撞上相似片段的概率上升），导致 v_top1 也出现重叠。

> **结论**：靠换统计量解决不了漂移，必须靠**多信号组合 + 可标定 + LLM 终审**。

### 1.3 实验 C：BM25 混合检索是否必要？

针对「稠密向量弱于精确标识符」这一 IR 共识做验证：

| 查询 | 向量 rank | 关键词 rank |
|---|---|---|
| HT-2026-0187 的交付日期 | 1 | 1 |
| 星辰科技的结算账号是多少 | 1 | 1 |
| XM-8842 项目谁负责 | 1 | 1 |
| E10392 是谁 | 2 | 1 |
| 10.20.31.47 在哪个可用区 | 1 | 1 |
| ZL202610384756.X 是什么专利 | 1 | 1 |

**top-3 命中：向量 6/6，关键词 6/6 —— 无显著差异。**

> 原因：bge-m3 对中文混合标识符的表征能力强；且当前语料规模下候选项少、排序容易。
> **不建议作为默认路径**，但保留为可开关能力（见 P2-2）。

### 1.4 实验 D：批量向量化收益

| 方式 | 耗时（120 块） |
|---|---|
| 逐块调用（当前实现） | 40.08s |
| 批量调用（batch_size=32） | **25.55s** |

**加速 1.6x**（CPU 推理；GPU 上收益会显著更大）。改动极小，零风险。

## 2. 模型选型的独立判断

> 这一节是我的设计主张，不照搬主流方案。

### 2.1 核心主张：**信号分工**，而不是「谁分数高听谁的」

主流 RAG 教程的套路是「rerank 分数做阈值门控」，本项目实测证明这在当前模型组合下是**错的**。
正确的职责划分应该是：

| 模型 | 类型 | 擅长 | 应承担职责 | 不应承担 |
|---|---|---|---|---|
| **bge-m3** | bi-encoder，向量召回 | 语义相似度的**绝对量纲稳定** | ✅ **门控**（该不该答） | 精排（粒度不够） |
| **bge-reranker-v2-m3** | cross-encoder，精排 | **相对排序**，见过 query+doc 全交互 | ✅ **排序**（哪段最相关） | ❌ 门控（绝对分不可信） |
| **LLM** | 生成 | 语义理解、判断是否答非所问 | ✅ **终审**（上下文是否真能回答） | 召回（成本高、不可控） |

一句话概括：**用 embedding 决定"能不能答"，用 reranker 决定"用哪段答"，用 LLM 兜底"答得对不对"。**

### 2.2 两级 No-Answer 设计（替代当前单阈值）

```
Tier 1  召回门（便宜、高召回）
        v_top1_sim >= answer_gate(默认 0.55)
        不过 → 直接 No-Answer，不消耗 LLM
              ↓ 通过
Tier 2  Reranker 排序（只排序，不判定）
        top-5 送 LLM
              ↓
Tier 3  LLM 终审（精确）
        prompt 明确要求：上下文不足以回答时输出 __NO_ANSWER__
        命中标记 → No-Answer
```

为什么这么设计：
- Tier 1 用**宽松**阈值（宁可放过，不可误杀）——实验证明误杀代价远大于漏拒
- Tier 2 不设阈值——reranker 只管用，避免它的绝对分造成二次误杀
- Tier 3 用 LLM 兜底——**基于上下文内容判断，不依赖分数分布，因此不受语料增长影响**，
  从根上解决实验 B 发现的阈值漂移问题

### 2.3 关于模型替换的判断

| 组件 | 现状 | 我的判断 |
|---|---|---|
| Embedding | bge-m3 (1024维) | ✅ **保留**。中文强、多语言、量纲稳定，是被实验验证过的门控信号来源 |
| Reranker | bge-reranker-v2-m3 | ✅ **保留但降级使用**。排序能力可靠，仅剥离其门控职责 |
| LLM | 仅 Ollama | 🔴 **必须改造**。见 P0-2 |

**不推荐**的改动（有依据才动，不为新而新）：
- ❌ 换更大 embedding 模型：当前召回 7/7，瓶颈不在 embedding
- ❌ 上 BM25/混合检索：实验 C 无增益
- ❌ 换 LLM 做 query rewrite：先补好门控与 prompt，rewrite 是 P2 的事

### 2.4 LLM 接入：OpenAI 兼容协议是唯一正确解

你的需求是「可能在局域网其他机器部署，或用第三方服务」。**不要为每家写适配器**——
OpenAI Chat Completions 协议已成为事实标准，一个客户端覆盖全部场景：

| 部署方式 | 接入形式 |
|---|---|
| 局域网另一台机器跑 Ollama | `http://192.168.x.x:11434/v1` |
| 本机 Ollama | `http://localhost:11434/v1` |
| vLLM / Xinference / LM Studio | 原生 `/v1/chat/completions` |
| DeepSeek | `https://api.deepseek.com/v1` |
| Moonshot / Kimi | `https://api.moonshot.cn/v1` |
| 通义千问（兼容模式） | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| SiliconFlow / OpenRouter / OpenAI | 各家 `/v1` 端点 |

配置驱动，零代码切换：
```
LLM_PROVIDER=openai_compat        # 或 ollama
LLM_BASE_URL=http://192.168.9.57:11434/v1
LLM_API_KEY=ollama                # Ollama 不需要真实 key，占位即可
LLM_MODEL=qwen2.5:7b
```

## 7. 第二轮实测：推翻两个判断，发现两个更根本的缺陷

v1.0 的 P0 全部实施完成后，用 **44 条查询（30 域内 + 14 域外）** 在真实语料上复测，
结果**推翻了 v1.0 的两个结论**，并暴露出比 No-Answer 阈值更上游的问题。
本节是本计划的权威结论，与 §1–§6 冲突处以本节为准。

### 7.1 推翻「相似度存在干净间隙」

v1.0 §1.1 基于 30 条查询得出「域内外相似度存在干净间隙（0.375 vs 0.4345），
推荐阈值 0.40」。样本扩大到 44 条后**间隙消失**：

| 样本 | 域外最高相似度 |
|---|---|
| 9 条（首轮诊断） | 0.3750 |
| 30 条 | 0.6113 |
| 44 条 | 0.6113 |

原因是补入了「形似干扰项」——「劳动合同法规定的试用期上限是多少」
「民法典对合同违约有什么规定」这类问题问的是**通用法律常识**，
检索到的却是本公司制度段落，相似度高达 0.64 ~ 0.71。

**结论：绝对阈值在结构上就无法区分这类查询，只能交给 Tier3 按内容判断。**
这也反过来验证了 §2.2 把「是否回答」的最终裁量权交给 LLM 是对的。

### 7.2 发现缺陷 A：分块粒度才是区分度的决定性因素

调优阈值时注意到异常：多数查询的 top1/top2/top3 相似度**完全相同**。
排查后发现根因不在阈值，而在切块：

```
技术服务合同.txt   477 字 → 1 块   （8 个条款共处一块）
财务报销制度.txt   413 字 → 1 块
运维安全规范.txt   388 字 → 1 块
员工手册.txt      550 字 → 2 块   （且切断了词语）
```

三份文档都小于 `chunk_size=500`，整篇塌成一块。后果是任意问题都命中同一块、
拿到同一个分数，检索完全丧失区分度。同批还发现边界硬切把
「员工应保守公司商业秘密」切成了上一块以「员」结尾、下一块以「司商业秘密」开头。

修复（**条款感知切块**，`app/ingestion/chunkers/clause_aware.py`）前后对比：

| 指标 | 通用递归切块 | 条款感知切块 |
|---|---|---|
| 块数（4 篇文档） | 9 | 25 |
| top1-top2 相似度间隙中位数 | 0.0015 | **0.0541**（36×） |
| 间隙 < 0.01 的查询占比 | 19/30 | **4/30** |
| 域内相似度中位数 | 0.5824 | 0.6266 |
| 域内最低相似度 | 0.4345 | 0.5438 |
| Tier1 误杀数（阈值 0.45） | 11/30 | **0/30** |

设计要点（**替代了 v1.0 规划的 P1-4 父子块**）：

- 以 `第X条` / `第X章` / `一、` / `（一）` / `1.2` / Markdown `#` 为一等边界，
  短条款原样成块，**不做跨条款切分** —— 早期实现按 `min_size` 链式合并短条款，
  结果 8 个条款又被并回 1 块，等于白切；
- 标题回填进 `section_title` 并拼在内容开头，使「打官司去哪儿解决」能直接
  匹配「第十二条 争议解决」；
- **重叠只在条款内部生效，绝不跨条款**；
- 无标题的引导段（文档名、缔约方）并入其后的第一个条款块。

> 为什么没做父子块（P1-4）：父子块解决的是「小块检索准但上下文少」的矛盾，
> 而本语料的病根是块太大、语义互相稀释。条款切块直接消除病根，且无需 schema
> 变更。若后续接入长篇无结构文档（如整本手册无条款编号），再考虑父子块。

### 7.3 发现缺陷 B：重复文档污染检索结果

语料里 7 篇文档只有 4 篇是不同内容：同一份合同存在 3 份副本（含改名重复上传）、
员工手册存在 2 份。9 个 chunk 里 4 个冗余（44%）。
重复块会原样挤占 top-k 名额 —— top_k=5 时实际多样性只剩 3。

根因：`_upsert_document` 用 `ON CONFLICT (id)`，而每次上传生成新的 uuid，
冲突永远不会触发。

修复分两层（详见 README「双层去重」）：

- 入库侧按原始文件 sha256 精确去重，`(workspace_id, content_hash)` 唯一索引，
  重复上传返回 409；`force=true` 走**覆盖重建**而非新增副本
  （新增副本等于把刚修好的问题又造回来）。
- 检索侧按 3-gram 重叠系数近似去重，处理不同文档间的相同套话条款。

> 度量选型踩过的坑：最初用 Jaccard，实测 30 字与其 35 字扩写版只有 0.794，
> 低于任何合理阈值，真正的近重复反而漏网。改用**重叠系数**
> `|A∩B|/min(|A|,|B|)`（0.964）—— 去重要回答的是「这块是否已被保留的某块
> 覆盖」，是不对称问题，Jaccard 惩罚长度差在这里是错的。

### 7.4 阈值最终取值：0.45（刻意不取 F1 最优点）

条款切块上线后重新标定（同批 44 条）：

| 阈值 | 误杀(域内被拒) | 放过(域外进入) | F1 | 备注 |
|---|---|---|---|---|
| 0.40 | 0 | 6 | 0.909 | |
| **0.45** | **0** | **5** | **0.923** | **采用** |
| 0.50 | 0 | 4 | 0.938 | F1 最优 |
| 0.55 | 1 | 4 | 0.921 | v1.0 默认值 |

取 0.45 而非 F1 最优的 0.50，理由是**余量**：域内最低相似度 0.5438，
0.50 只剩 0.044 余量，而阈值随语料规模漂移是实测过的（15→35 篇时域外最高
0.5256→0.5996）。0.45 留 0.094 余量。

同时明确 F1 不是这里的正确目标：**误杀与放过不对称**。误杀 = 用户拿不到答案
且无解；放过 = 多跑一次 LLM，由 Tier3 判回拒答。应按「召回优先」定阈值。

### 7.5 附带修复：测试会抹掉开发库（事故）

`tests/test_pipeline.py` / `test_vector_store.py` 的 `clean_tables` fixture
无条件整表 `DELETE`（无 WHERE），而 `TEST_DATABASE_URL` 默认指向开发库
`knowledgepilot`。后果：**跑一次 pytest 就会抹掉开发者整个知识库** ——
本次优化过程中真实发生过，7 篇文档与全部 chunk 被清空。

修复：测试默认走独立库 `knowledgepilot_test`（自动创建 + 灌 schema）；
`conftest.py` 拒绝在非测试库上运行（除非显式 `KP_ALLOW_DESTRUCTIVE_TESTS=1`）；
因为 `app/db.py` 在 import 期就建引擎，`DATABASE_URL` 必须在 conftest 的
**模块导入阶段**设置，放在 fixture 里会来不及。

### 7.6 附带修复：上传后查询 404 的竞态

`POST /upload` 返回 `document_id`，但 documents 行由 worker 的 `run_ingestion`
才创建，前端拿到 id 立即轮询会 404。已改为上传时即落行（`status=pending`）。

## 8. 第三轮实测：接真 LLM，补上 7.7 的未验证项

### 8.1 环境：局域网 Ollama（192.168.9.26）

192.168.9.26 上装了 Ollama。探测结果：

| 探测 | 结果 |
|---|---|
| `GET /api/tags`、`GET /v1/models` | 200，约 7ms |
| 可用模型 | `qwen3-vl:30b-a3b-instruct-q4_K_M`（19.6GB）、`qwen3-vl:30b-a3b-instruct-q8_0`（33.5GB）、`bge-m3` |
| `bge-m3` 走 `/v1/chat/completions` | ❌ `{"error":{"message":"\"bge-m3\" does not support chat"}}` |
| `bge-m3` 走 `/api/embed` | ✅ 返回 1024 维向量 |

**「b3 模型」= `bge-m3`，它是 embedding 模型，不能对话。** 这是本轮第一个
需要纠正的认知：名字里带 "b3"／"m3" 的是向量模型，生成必须另选 chat 类模型。
（这段排查经验已写进 README「快速开始 §3」的排查清单。）

接入配置写在 `backend/.env`（该文件已 gitignore）：

```
LLM_PROVIDER=openai_compat
LLM_BASE_URL=http://192.168.9.26:11434/v1
LLM_MODEL=qwen3-vl:30b-a3b-instruct-q4_K_M
LLM_API_KEY=ollama          # 占位值，Ollama 不校验
LLM_TIMEOUT=180             # 30B 冷启动约 26s，120s 不够
```

> 坑：`.env` 必须放在 `backend/` 下。pydantic 的 `env_file` 相对**当前工作目录**
> 解析，而服务从 `backend/` 启动；仓库根目录的 `.env.example` 只是模板，不会被读。

延迟实测：冷启动 26.3s（19.6GB 载入），之后 2.8~4.4s，44 条评测平均 7~8s/条。

### 8.2 推翻「未通过项是 Tier3 缺位」——7 条里有 5 条是我标注错了

接上真 LLM 后跑 44 条：37/44，**域外 14/14 全部通过**（7.7 里推断应由 Tier3
拦截的 5 条，实测确实全被拦下，推断被证实）。但冒出 7 条域内拒答。

动手改之前先查证：把每条的 top3 检索块全文拉出来逐条核对，**语料里到底有没有
答案**。结论是 5 条根本没有：

| 被拒查询 | 语料实况 | 判定 |
|---|---|---|
| 加班有钱吗 | 全文 **0 处**「加班」 | 标注错 |
| 报销单要谁签字 | 全文 **0 处**「签字」 | 标注错 |
| 发票丢了还能报吗 | 「发票」仅 1 处，且是「餐补无需提供发票」 | 标注错 |
| 年假没休完会怎样 | 只写年休假天数，未提未休如何处理 | 标注错 |
| 账号密码忘了找谁 | 只写权限原则与更换周期，无联系人 | 标注错 |
| 这合同能作废吗 | 第十条「有权单方解除」 | **真误杀** |
| 差旅报销要几个工作日 | 第二章「次周周五统一打款」 | 边界 |

这批误标的价值恰恰在此：它们**看起来**都像公司知识库该答得上的问题，检索也
确实拉回了高度相似的段落，但语料就是没写。能识别出「相似但答非所问」正是
拒答机制该干的事 —— 若把它们算作失败，等于奖励系统去硬编答案。

### 8.3 缺陷 C：Tier3 的拒答错误是两类性质相反的错配

对剩下 2 条真误杀做提示词 A/B。**第一版用精选上下文，结论不可信** —— 手写
上下文下「对方不给钱怎么办」旧提示词也答得出来，而全量跑时它拒答了；反之
「国家法定年休假是几天」在精选上下文下被误放行，全量跑却正确拒答。改用
`scripts/` 里走真实管线（embed → 检索 20 → 去重 → rerank → top5）生成的上下文
重做，才拿到可信对比：

| SYSTEM_PROMPT | 主指标 | 域内 | 域外误放行 |
|---|---|---|---|
| 原始版 | 41/42 | 22/23 | 0 |
| v2：只加口语→书面语映射 | 41/42 | 23/23 | **1** ❌ |
| v3：两类错配分开写 | **42/42** | **23/23** | **0** ✅ |

（口径：44 条剔除 2 条 `BOUNDARY`；5 条首版误标的查询已按语料查证改判拒答。
三个变体共用同一套标注与同一批真实检索上下文 —— 混用不同口径算出来的数字
不可比，这点我在第一次填表时就搞错过。）

**v2 净零，这是本轮最关键的一条发现。** 单纯放宽映射虽然修好了「作废→解除」，
却让「一般公司的违约金是怎么算的」漏了出去 —— 模型拿本公司合同的违约金条款
去回答「一般公司」的普遍做法。

所以拒答错误不是单一原因，而是两个正交维度：

- **甲类 · 术语错配**（口语 vs 书面语）：应当**对齐后回答**。
- **乙类 · 作用域错配**（内部规定 vs 外部通用）：**不得对齐，必须拒答**。

只写一个方向必然顾此失彼。v3 同时写两条：甲类给映射示例并允许「一步直接推理」
（禁止跨片段拼装），乙类列出作用域越界信号词（`一般`/`通常`/`劳动法`/`民法典`/
`行业标准`/`行情`…），命中即拒答。

### 8.4 缺陷 D：温度未显式置 0，判定是随机的（代价最小、最易忽略）

v3 提示词在 A/B 脚本里跑出 43/44，走 API 端到端却只有 41/44 —— **同样的查询、
同样的语料，两次跑结果不一样**。

根因：`OpenAICompatLLM` 没下发 `temperature`，Ollama 取默认 ≈0.8。

| 查询 | 默认温度 ×5 | `temperature=0` ×5 |
|---|---|---|
| 年假没休完会怎样 | 拒答/拒答/拒答/**回答**/拒答 | 拒答 ×5 |
| 账号密码忘了找谁 | 拒答/**回答**/**回答**/拒答/拒答 | 拒答 ×5 |

域外成绩因此在 17/19 ~ 19/19 之间随机波动。对知识库而言「同一个问题两次问出
不同结论」比答错更伤信任。修复：新增 `LLM_TEMPERATURE`（默认 `0.0`），两个
provider 都显式下发（Ollama 原生走 `options.temperature`）。

置 0 后**连续两轮 44 条评测逐条一致**（唯耗时不同）。

### 8.5 遗留：二元拒答浪费「部分命中」

`temperature=0` 后剩 2 条域内拒答，都属于同一个模式 —— 语料命中了正确条款，
却偏偏没有用户问的那个精确维度：

- 「差旅报销要几个工作日」→ 资料写「次周周五统一打款」：有节点，无数目。
- 「违约最高赔多少」→ 资料写「违约金壹拾万元 + 直接经济损失」：损失不封顶，
  故「最高」在语料里并不存在。

这两条二选一都算不上错，评测中标记为 `BOUNDARY` 不计入主指标。真正的问题是
产品形态：明明检索到了正确条款，却只能回「不知道」。

**下一步可选**：三态输出（完整回答 / 部分回答 / 拒答），对「部分」仍置
`no_answer=true` 但附相关条款作为线索。**风险**：三态给形似干扰项多留一个可误踩
的档位 ——「一般公司的违约金是怎么算的」完全可能被判成「部分」而非「拒答」。
必须先设计好作用域约束，否则会牺牲现在 19/19 的域外成绩。本轮不做。
